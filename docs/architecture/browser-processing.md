# IFCCAD Explorer architecture

The Explorer inspects one IFCCAD, DXF or DWG source at a time through the
production browser/WASM adapter. This page consolidates its processing and
inspection design. The [Explorer guide](../../format-explorer/README.md) owns
usage, downloads, development commands and deployment prerequisites;
[example recipes](../../examples/README.md) own the curated catalogue.
Format semantics remain in schemas/conformance and current code/tests.
OCDraw files and explicit retired route choices return `OCDRAW_PARKED` before
active processing; see [parking](../ocdraw-parking.md).

## Processing responsibilities

The flow is local source bytes and explicit settings -> worker/WASM -> production
reader or converter -> validated native document, diagnostics and inspection
data -> frontend views. CAD preview consumes verified exported DXF/DWG bytes.

| Component | Responsibility |
| --- | --- |
| Workspace/session controller | Selected source, settings, requests, pane state and selection |
| Worker and `browser` WASM adapter | Byte IO, limits, cancellation, format/version selection and production reader/converter calls |
| IFCCAD inspection adapter | Typed drawing meaning, composed IFCX nodes, references and source contributions |
| Shared contents/inspector | Labels, bounded browsing, stable selection, reference navigation and JSON scopes |
| Conversion reports/settings | Applied options and separate input/output evidence |
| CAD preview controller/bridge | Generated bytes, complete request identity, readback-qualified mappings and viewer session |

The core owns logical validation, encoding and storage without a CAD runtime.
`ifccad-convert` owns CAD semantics and loss diagnosis; companions own their
specialized preparation. Presentation metadata belongs to the adapter rather
than a new native extension protocol. CAD-to-IFCX header provenance uses the
source name, Explorer author and caller-supplied browser UTC timestamp.

Files stay on the device. Processing has no drawing-upload or server conversion
API. Optional feedback is a separate explicit request; its fields and deployment
conditions are described in the guide. Source file names, drawings and screenshots
are not automatically included with that feedback.

## Native opening and output

CAD input defaults to IFCCAD. IFCX/JSON (`.ifcx` or `.ifcx.json`) uses the strict
source-aware reader, LaterWins composition and its bundled experimental import.
CBOR and CBOR + Zstd use their strict production readers. The browser explicitly
enables the optional Zstd feature; this is separate from default core/WASM
feature selection. Input and decompressed CBOR are capped at 64 MiB.

JSON loading retains exact original bytes, the complete composed graph and the
validated drawing projection separately. Original IFCX download retains foreign
nodes and source contributions. Fresh binary output encodes only the validated
CAD projection. Binary inspection labels decoded JSON/nodes honestly and never
invents original IFCX fragments. Same-encoding binary download retains validated
input bytes; JSON output from binary reconstructs an IFCX drawing. See the
[lifecycle](../experiments/ifccad-document-lifecycle.md) and
[CBOR guide](../experiments/ifccad-cbor.md) for these boundaries.

CAD export is decoded and version-checked before download. The IFCCAD route
also converts actual CAD readback to production-readable IFCCAD. A failed output
check exposes no checked CAD download but retains valid input/native download.
Structural success does not certify exact geometry through the file codec or
host rendering. Contradictory BLOCK markers remain errors; no silent source
repair is implied by preview success.

## Source, requests and result state

One selected source owns a generation identity. A new source clears previous
results; cancellation terminates worker work and invalidates pending file reads,
example fetches, progress and results. A late reply cannot replace the current
drawing. Loading presents actual reported phases without fabricated percentages.
Source/conversion failures retain their own report; previous contents cannot be
presented as the new source. Any exposed raw invalid contents must be labelled
unvalidated, and parse failure must not manufacture a semantic tree.

The applied request identity includes source, route, direction, CAD format/version,
tolerance and relevant loss/preservation/recovery settings. Output caches must
use that identity. Draft settings become effective only on Apply; stale output
cannot be downloaded as though it used the new settings. Output-only changes
retain original input conversion options and native validity.

CAD opening initializes output format/version from production reader provenance
where supported, preferring original DWG provenance over a normalized document
version. Unsupported source versions retain a supported target with an explicit
note. Native input retains the current CAD output selection. Format/version
choices are shared by preview and CAD download.

Typed spline capture starts enabled for each newly selected CAD source, with
explicit opt-out. Library capture defaults and restore qualification remain
independent; see [preservation](../preservation.md). Partial opening is an explicit
retry after an entity-local failure. It retains omission/error evidence and a
persistent notice; exports contain only retained content. Shared structural and
final validation failures remain fatal. A new source restores ordinary import.

## Inspection model and composition

Document structure follows validated CAD ownership and authored draw order,
including unused resources and shared definitions. Type groups are navigation
records; they are not native nodes and never reorder stored contents. Storage
structure shows each composed IFCX node once by its complete path. Path prefixes
do not create `children` relationships. Envelope/header/import/schema information,
foreign nodes and foreign attributes remain accessible on their actual records.

Both structures use one selection identity. Full-width IDs cross the JavaScript
boundary as exact strings; display labels, array positions and CAD handles are
not native identity. A block instance links to a shared definition without
becoming its owner. General references navigate shared/cyclic targets without
recursive duplicate trees. Recognized typed/schema references establish edges;
an arbitrary string does not. Stored `inherits` is distinct from ownership and
does not imply general inherited-value evaluation.

Properties exposes stored values, meanings, units and original keys. Relationships
exposes typed incoming/outgoing links and owner/draw position. Source exposes the
effective node and ordered original contributions. The reader composes repeated
paths before CAD validation: immediate keys in `children`, `inherits` and
`attributes` merge in file order; repeated keys replace whole values, including
entire geometry/appearance objects. Other node fields replace as whole values.
Null inheritance entries remove their keys, while null child/attribute markers
follow the reader's existing rules. The frontend neither deep-merges geometry
nor invents deletion, inheritance or external-import behavior.

Fragment counts include identical contributions. Source indices are used when
accurate byte/line locations are unavailable. Pretty JSON, composed JSON and
inspection JSON remain explicitly distinct from original byte spelling.
Selection and JSON scope persist through view changes. Opening a reference
reveals its target and ancestors; expanding a property keeps its owning record.
Primitive property labels/values remain plain text rather than new selections.
Producer bounds declarations, derived quality, conversion accuracy, preservation
and display evaluation remain separate evidence. Hatch inspection explains
stored contours and source references without certifying filled topology.

One source snapshot and indexed references serve a result. Large collections use
bounded lists; the tree retains selected ancestor anchors without mounting all
preceding siblings. Search/layer filters preserve source order and never modify
the drawing. Reverse CAD selection reveals the same native identity and can
clear a hiding filter without starting conversion. The guide documents the
adaptive tree/list/inspector interaction.

## Conversion evidence and tolerance

Input conversion owns CAD reading, CAD-to-native diagnostics, omission reports
and native validation. Output conversion owns native-to-CAD export, restoration
and written-CAD readback. Native opening reports direct validation without an
invented input conversion. Output failure never replaces the input report or
changes native validity. Viewer-session failure remains separate from either.
Reports show not-performed operations as such and retain diagnostic codes,
source locations, original reasons and numerical intervals. Located messages
link to native records only through unambiguous mappings.

Default tolerance is exactly `1e-9` in each coordinate domain; Exact is zero.
Custom physical limits require known Model units or fixed Paper plot mappings,
with an explicit independent coordinate fallback for unknown domains. Medium
dimensions alone provide no Paper scale. Effective domain limits come from
conversion evidence, not preview arithmetic. Settings can apply to both
conversion boundaries or input/output separately. `conversionOptions` and
optional `exportConversionOptions` retain those independent choices.

Tolerance does not alter native validity, semantic coverage, clip eligibility
or Allow/Reject policy. No failure automatically raises it. Within-limit rounding,
proven exceedance and incomplete numerical proof retain their actual production
classification. See [accuracy policy](../geometry/shared-geometry.md#accuracy-policy).

## CAD session and selection

After successful native opening/conversion, CAD output preparation runs in the
background independently of the drawing pane. The viewer initializes lazily
when visible and shares prepared output with download. Pane changes preserve
camera, selected record and the CAD session. New source/settings/cancellation
invalidate unfinished output work. Open CAD Studio receives actual DXF/DWG bytes;
it does not edit the native IFCCAD source. Original CAD and generated CAD remain
separate documents. Existing edited sessions are preserved by the bridge;
viewer restart and save/discard remain explicit actions.

Transient `viewerSelection` metadata binds complete IFCCAD paths to CAD handles
and actual layout names only after readback verifies kind and owner. Shared
block-definition contents and unmapped/skipped records have no direct link.
Forward selection verifies the generated document, activates the exact owner
layout, selects and reads back the result. Native layout selection activates
Model or the validated Paper name and clears element selection. Other resources
do not infer a layout. Already-active layouts retain camera; the bridge does
not fit, reload or regenerate the drawing to select a record.

Requests are serialized and later intent supersedes stale replies. Existing CAD
commands/modals are not interrupted. Missing layouts and rejected names produce
unavailable status rather than selection in a different coordinate space. The
recorded CTAB qualification uses the pinned
[dispatcher](https://github.com/HakanSeven12/OpenCADStudio/blob/0d023d267bc5b7afeca3b54e98875b0efd4f3926/src/app/control/mod.rs)
and [handler](https://github.com/HakanSeven12/OpenCADStudio/blob/0d023d267bc5b7afeca3b54e98875b0efd4f3926/src/app/commands/plotvars.rs),
which consume the complete remaining name; control characters or trimmed
leading/trailing whitespace cannot be accepted as exact names by that mechanism.

Reverse observation uses the viewer state API at 300 ms while the generated
drawing is visible and focused, with pointer/keyboard/focus wake hints. It pauses
around programmatic operations and seeds acknowledged selections to avoid echo.
In-flight reads cannot publish after document, focus, visibility or generation
changes. One mapped handle in the matching layout reveals the native record
without invoking forward selection. Empty/multiple/unmapped selections and
original/external CAD tabs retain the last inspection. This is a transient
selection association, not CAD-to-IFCCAD edit synchronization.

## UI and verification boundaries

The shell follows the OpenAEC application template's visual direction without
requiring a desktop runtime or frontend-framework migration. Views reuse the
same contents, reports and CAD session. Resizing, keyboard navigation, focus
management, narrow-screen reflow and Dutch/English labels remain application
requirements. File-derived values render as text; graph/import links do not
fetch arbitrary imports. Same-origin parent/frame/token and current-document
checks guard viewer messages. Storage failures must not disable current-session
language/theme settings. Settings never rewrite stored names, JSON keys or codes.

The [example registry](../../examples/README.md) must account for integrated native
families/variants with strict readback. Example refreshes do not extend semantic
coverage. The earlier separate graph-root mockup and OCDraw storage design are
superseded; a future node-and-edge visualization is optional and requires a
useful inspection case. No generic IFCX editor or new preservation/encoding
protocol is selected by this architecture.

Focused frontend/worker/bridge tests and applicable real-reader/WASM smoke checks
exercise cancellation, exact identity, composition, owner/order, independent
input/output settings, selection mappings, session preservation and failure
separation. Documentation consolidation itself runs no implementation gate or
measurement. Development sequencing remains in [ROADMAP.md](../../ROADMAP.md).
